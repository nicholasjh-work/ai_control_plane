# SQL Safety and Semantic Allowlist

This document describes the SQL safety layer implemented in `ai_control_plane`, including SELECT-only enforcement, blocked statement types, parser-based validation using sqlglot, semantic view allowlists, and the validation API endpoint.

---

## 1. Purpose

To prevent arbitrary or mutating SQL statements from being submitted to the service by agents, users, or automated pipelines. The safety layer acts as a structural guardrail: any SQL that does not conform to the SELECT-only, allowlisted-view contract is rejected before it can reach a database, regardless of who or what generated it.

---

## 2. Business Use Case

In AI-assisted data operations, there are scenarios where agents or users may supply SQL queries as part of a workflow: reporting requests, ad-hoc analysis, data quality checks. Without a validation layer, a malformed or adversarial query (whether generated by an LLM or submitted directly) could attempt to mutate, drop, or exfiltrate data.

The semantic allowlist solves a second problem: even a well-formed SELECT can access tables that should not be exposed. By maintaining an explicit list of permitted view names and rejecting any query that references a table outside that list, the service enforces a data access boundary that cannot be bypassed by constructing a valid SELECT.

---

## 3. Operating Model

The SQL safety layer operates as a stateless validation service. It:
1. Receives a SQL string
2. Parses it using sqlglot
3. Validates it against statement type rules and the allowed table list
4. Returns a `ValidationResult` with `allowed: bool` and `reason: str`

No query is ever executed by this layer. It is purely a validator. Execution, if any, is the responsibility of the caller.

---

## 4. Architecture

```
POST /v1/sql/validate
    │
    ├─ SQLRequest (Pydantic model: {"query": str})
    │
    ├─ validate_query(sql)               — app/sql/safety.py
    │       ├─ sqlglot.parse(sql)
    │       ├─ Single-statement check
    │       └─ _check_statement(statement)
    │               ├─ Blocked type check (INSERT, UPDATE, DELETE, DROP, CREATE, ALTER, TRUNCATE, Command)
    │               ├─ SELECT-only check
    │               ├─ Table name allowlist check (per exp.Table node)
    │               ├─ Subquery recursion (validates inner SELECT)
    │               └─ UNION recursion (validates both sides)
    │
    └─ JSONResponse: {"allowed": bool, "reason": str}
              HTTP 200 if allowed
              HTTP 422 if blocked
```

The allowed table list is loaded at startup from `app/config/semantic_views.json`. The safety module has no database connection and no runtime state.

---

## 5. Control Design

### Implemented: Statement type blocking

The following statement types are rejected by class-level isinstance check against sqlglot expression types:

| Statement type | sqlglot class | Blocked |
|---|---|---|
| INSERT | `exp.Insert` | Yes |
| UPDATE | `exp.Update` | Yes |
| DELETE | `exp.Delete` | Yes |
| DROP | `exp.Drop` | Yes |
| CREATE | `exp.Create` | Yes |
| ALTER | `exp.Alter` | Yes |
| TRUNCATE | `exp.TruncateTable` | Yes |
| Raw command | `exp.Command` | Yes |
| SELECT | `exp.Select` | Allowed (subject to table check) |
| UNION of SELECTs | `exp.Union` | Allowed if both sides are valid |
| Any other type | — | Blocked with type name in reason |

### Implemented: SELECT-only enforcement

Any parsed statement that is not an `exp.Select`, `exp.Union` (of SELECTs), or a blocked type is rejected with a reason string of the form `"{TYPE} statements are not allowed"`.

### Implemented: Semantic view allowlist

The current allowlist (from `app/config/semantic_views.json`):

```json
{
  "allowed_tables": [
    "v_ticket_summary",
    "v_agent_performance",
    "v_audit_summary",
    "v_routing_decisions"
  ]
}
```

All four entries are named views (prefixed `v_`), not base tables. Any `exp.Table` node whose `name` (lowercased) is not in this set is rejected with the reason: `"table '{name}' is not in the allowed views list"`.

### Implemented: Subquery validation

`_check_statement` recursively validates all `exp.Subquery` nodes within a SELECT. A subquery referencing a blocked table or containing a mutation statement is rejected, even if the outer query is a valid SELECT.

### Implemented: UNION validation

UNION queries are unwrapped. Both the left and right sides are individually validated through `_check_statement`. A UNION of two valid SELECTs over allowed tables is permitted. A UNION where either side is invalid is rejected.

### Implemented: Multi-statement rejection

`sqlglot.parse()` returns a list. If the list contains more than one statement (e.g., `SELECT ...; DROP TABLE ...`), the query is rejected with `"multiple statements are not allowed"`.

### Implemented: Unparseable query rejection

If `sqlglot.parse()` raises any exception, or if the parsed result is empty or `None`, the query is rejected with `"unparseable query"`.

## 6. Governance Workflow

```
SQL query submitted to POST /v1/sql/validate
    │
    ├─ Parse with sqlglot
    │       └─ Failure → {"allowed": false, "reason": "unparseable query"}
    │
    ├─ Single-statement check
    │       └─ Multiple → {"allowed": false, "reason": "multiple statements are not allowed"}
    │
    ├─ Statement type check
    │       └─ Blocked type → {"allowed": false, "reason": "{TYPE} statements are not allowed"}
    │
    ├─ SELECT enforcement
    │       └─ Not a SELECT/UNION → {"allowed": false, "reason": "{TYPE} statements are not allowed"}
    │
    ├─ Table allowlist check (for each exp.Table node)
    │       └─ Not in allowed_tables → {"allowed": false, "reason": "table '{name}' is not in the allowed views list"}
    │
    ├─ Subquery recursion (for each exp.Subquery)
    │       └─ Inner statement fails → propagate failure
    │
    └─ UNION recursion (for each side)
            └─ Either side fails → propagate failure

All passing → {"allowed": true, "reason": "ok"}, HTTP 200
Any failure → {"allowed": false, "reason": "..."}, HTTP 422
```

## 7. Implementation Workflow

The safety module has no external dependencies beyond `sqlglot` (in `requirements.txt`) and a read of `app/config/semantic_views.json` at import time.

To add a new allowed view:
1. Open `app/config/semantic_views.json`
2. Append the view name to the `allowed_tables` array
3. Restart the service (module-level load)

To test the validation endpoint directly:

```bash
# Valid SELECT against an allowed view
curl -X POST http://localhost:8000/v1/sql/validate \
  -H "Content-Type: application/json" \
  -d '{"query": "SELECT audit_id, created_at FROM v_audit_summary WHERE resolution = '\''succeeded'\''"}'
# Returns: {"allowed": true, "reason": "ok"}

# INSERT attempt
curl -X POST http://localhost:8000/v1/sql/validate \
  -H "Content-Type: application/json" \
  -d '{"query": "INSERT INTO v_ticket_summary (id) VALUES (1)"}'
# Returns HTTP 422: {"allowed": false, "reason": "INSERT statements are not allowed"}

# Query against a table not in the allowlist
curl -X POST http://localhost:8000/v1/sql/validate \
  -H "Content-Type: application/json" \
  -d '{"query": "SELECT * FROM raw_user_pii WHERE ssn IS NOT NULL"}'
# Returns HTTP 422: {"allowed": false, "reason": "table 'raw_user_pii' is not in the allowed views list"}
```

The examples above reflect actual eval harness cases (eval_019 through eval_024) and their confirmed outcomes.

## 9. Workplace Application

The SELECT-only, view-allowlist pattern is applicable wherever AI-generated or user-supplied SQL queries need to be validated before reaching a database. Common applications:

- **LLM-to-SQL pipelines:** An LLM generates a query from natural language. Before passing the query to a database connection, it goes through this validation layer to catch hallucinated table names and mutation attempts.
- **Self-service analytics portals:** Users can submit queries but are restricted to a curated set of views that represent pre-approved, governed data surfaces. Base tables and sensitive columns are never in the allowlist.
- **Agent tool calls:** An agent equipped with a SQL tool calls this validator before executing any query it generates. The validator acts as a permission boundary between the agent and the database.

The separation of validation from execution is intentional and important. The validator makes a yes/no decision. The caller decides what to do with that decision.

---

## 10. Limitations

- The allowlist is a flat list of table names. It does not support column-level restrictions. A SELECT that reads sensitive columns from an allowed view will pass validation.
- sqlglot parsing is dialect-aware but the dialect is not explicitly set. Queries in unusual dialects may parse differently than expected.
- Views that alias or wrap restricted tables are not analyzed by the validator. A view named `v_ticket_summary` could internally query any table; the validator only checks the name referenced in the query, not the view definition.
- The validator does not handle all possible SQL injection patterns. It is not a security substitute for parameterized queries or database-level access control.
- There is no rate limiting or quota enforcement on the `/v1/sql/validate` endpoint.
- The validator does not currently support `WITH` (CTE) clauses. A CTE that wraps a mutation statement may not be caught.

---

## 11. What This Does Not Claim

- The SQL safety layer does not execute queries. It validates and returns a decision.
- The allowed views (`v_ticket_summary`, `v_agent_performance`, `v_audit_summary`, `v_routing_decisions`) are configuration entries. The corresponding database views may or may not exist in any connected database.
- The validator is not a substitute for database-level access control (row-level security, column masking, role-based permissions).
- sqlglot is an open-source SQL parser. Its accuracy depends on its parser implementation. The validator's behavior on edge cases is bounded by sqlglot's parsing behavior.
- No production query volume or security certification is claimed.

---

## 12. Extension Path

- **Column-level allowlist:** Parse `exp.Column` nodes and validate against a per-view column allowlist loaded from `semantic_views.json`.
- **CTE support:** Detect `exp.With` clauses and recursively validate the CTE body through `_check_statement`.
- **Dialect specification:** Pass an explicit `dialect` parameter to `sqlglot.parse()` based on the target database (e.g., `dialect="postgres"`).
- **Parameterized query support:** Add a query template mode where `?` or `$1` placeholders are validated without literal values.
- **Query logging:** Log every validated query (without literal values) to the audit trail for operational visibility.
- **Integration with agent tool dispatch:** Wire `validate_query()` into a `SQLToolAgent` that generates and validates a query before passing it to a database connection.

## 13. Interview Talking Points

- **Why use a parser instead of a regex to enforce SELECT-only?** A regex cannot reliably parse SQL. Multi-statement injections, comment-based bypasses, and dialect variations make regex SQL filtering brittle. sqlglot produces an AST that reflects the actual parsed meaning of the query. Type checks against AST node classes are reliable across a wide range of SQL constructs.
- **What does the allowlist actually protect?** It prevents any query from accessing tables outside the approved view set, including base tables, system tables, and tables containing raw PII. Even if an LLM generates a valid SELECT against `raw_user_pii`, the validator rejects it because that table name is not in `allowed_tables`.
- **How would you add a new reporting view?** Add the view name to `app/config/semantic_views.json` and restart the service. No code change is required. The allowed table set is loaded at module import from that file.
- **What happens if a UNION query embeds a mutation on one side?** The UNION recursion in `_check_statement` validates both sides. A `SELECT ... UNION DROP TABLE ...` would fail because DROP is not a SELECT and is in the blocked type list. The rejection propagates back through the UNION check.
- **Why does the endpoint return HTTP 422 for blocked queries?** 422 Unprocessable Entity is the appropriate status for a semantically invalid request — the query is syntactically parseable but violates the validation contract. 400 would suggest the request was malformed; 403 would suggest a permissions error. 422 is the most precise signal.
